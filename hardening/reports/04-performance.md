# 04 Performance

Agent 04, branch `hardening/04-performance`, cut from `fullstack-hardening` at `4bc66d1`, 21–22 November 2026. Local measurements only: nothing was deployed and nothing touched Azure, Cosmos index policy or DNS. Production received three read-only GET requests (the sign-in page and one script, to check compression). Every timing below is **local, not production**: the test-only host `ParishLife.EndToEnd` (Release build, Development environment, local file storage, HTTPS with the untrusted development certificate ignored by the tools), Chromium 1194 from Playwright, k6 and the host on the same Mac.

Tools and how they were used:
- **Document operations per request:** new test `ParishLife.IntegrationTests/RequestCostTests.cs` with a counting decorator around the document store (`Support/CountingDocumentDatabase.cs`); it also prints which documents a request reads more than once.
- **Browser requests and timings:** a Playwright script (`scratchpad`, not committed) counting API requests, transfer and time to the last API answer on the public homepage, a parish page, the sign-in page and the priest's portal load, with and without 80 ms of added latency (Chrome DevTools network emulation). The test host was given 20 synthetic verified parishes ("Load test parish N", created through the API as the fixture operator, deleted with the host's temporary storage).
- **Lighthouse 12.8.2** through `npx -y lighthouse@12.8.2` (npm cache only; not added to the project) with `CHROME_PATH` set to Playwright's Chromium, `--only-categories=performance`, mobile (default throttling) and `--preset=desktop`.
- **k6 2.4.0** with the new `tools/load/parishlife.k6.js`.

## A. Summary

- **Before:** the public homepage made 151 API requests with 20 parishes (7 per parish), a parish page 156, and error responses held their connection for 12 s; the portal loaded its 12 modules one after another, on sign-in and after every save; every visitor's public read hit storage, and the directory read 2 documents per parish; production serves the 1.67 MB portal script uncompressed, and the portal downloads every screen before the sign-in form shows (mobile LCP 14.9 s on `/`).
- **Fixed in my files:** homepage 151 → 71 requests and parish page 156 → 35; held 404s released at once (network idle 12.8 s → 1.2 s); modules load together (portal shown after 1.31–1.35 s instead of 2.83 s at 80 ms latency); a server cache for the anonymous public reads, cleared at once by any public write (a repeated directory read now touches no document; visitor p95 at ten times the pilot peak 249 → 124 ms); a one-query read of every parish's directory documents; a k6 load test.
- **Ready as patches for their owners, measured with them applied:** compression (03) and route-level code splitting (05) take `/` from mobile LCP 14.9 s to 6.4 s and desktop 2.8 s to 1.3 s; the batched directory service (03) makes the directory cost 1 read + 3 queries whatever the number of parishes.
- **Still failing:** mobile LCP ≤ 2.5 s is not met on any main page in the lab, even with every patch (best: a parish page at 3.2 s). The next blockers are a late-discovered background image and render-blocking Google Fonts in the page heads (06), and no CDN (owner). My committed changes cut requests and time to data but do not move LCP (it is paint-bound: scripts, styles, one background image). CLS (≤ 0.02) passes everywhere; TBT (the lab stand-in for INP) is under 200 ms except the homepage on mobile with 20 parishes (165–248 ms, before and after).
