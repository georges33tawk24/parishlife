# Custom forms and workflows (W01, W02)

Parish custom workflows for repeatable office processes (for example event proposal, equipment repair, purchase request). The contract is the **proposed** S21.04 / S28.07–12 / WF49 / FM49 / P27 material, implemented as a mechanism; none of it is owner-approved policy and no real parish template is seeded. Every route needs current MFA (recovery sessions are refused), the exact parish permission in the selected capacity (selected appointment or explicit grant, never a union), and paid `office` coverage. Unauthorized or unknown resources answer `resource_not_found`.

## Forms (W01)
- Form fields reuse the event-registration field model (`RegistrationField`): types `Text`, `Choice`, `Boolean`, `Number`, `Date`; `required`; choice `options`; conditional show (`visibleWhenField`/`visibleWhenValue`) and, new, conditional require (`requiredWhenField`/`requiredWhenValue`). Conditions must reference an *earlier* field and a value it can hold (a choice option or `true`/`false`); a field cannot be both always and conditionally required. The new members are omitted from JSON when null, so existing registration forms and request fingerprints are unchanged. Registration forms gain conditional require and the stricter condition check too.
- Rules are evaluated on the server against the pinned version: unknown answers, answers to hidden fields, missing required/conditionally required answers and type mismatches are refused.
- Privacy class per field: `restrictedFieldKeys`. Restricted answers are stored as purpose-bound protected data (`ParishLife.WorkflowAnswers.v1`, per parish and run) and shown only to process owners, the starter (while still holding the start permission) and actors holding the permission of a step marked `viewsRestricted`; everyone else gets them omitted with the keys in `redactedFieldKeys`. Lists and the worklist never include restricted answers.

## Definitions (process owner: `workflows.manage`)
- `POST /api/parishes/{parish}/workflows` create (title + template), `GET` list, `GET|PUT …/{definition}` read / save the working draft (current `Version` required).
- `POST …/{definition}/publish` publishes exactly the reviewed draft `Version` as a new immutable numbered version; older versions stay readable and runs keep the version they started with.
- `POST …/{definition}/mode` with `Open`, `PausedNew` (no new runs, existing runs continue) or `SafetyStop` (no new runs, no step results, no resume or reopen; pause and cancel stay possible), with a reason.
- `GET …/{definition}/versions/{version}` is the starter's form preview, readable by process owners, start-permission holders and the version's step actors.
- Template validation: start and step permissions must be existing parish permissions (a step only *requires* an authority the actor already holds; the builder never grants one); 1–20 steps with distinct keys; step branch conditions (`whenField`/`whenValue`) use the same reachable-condition rule; at least one unconditional step; restricted keys must be form fields.

## Runs (W02)
- `POST /api/parishes/{parish}/workflows/{definition}/runs` — needs the version's start permission, `Open` mode and the currently published `versionId` the starter viewed (`workflow_version_changed` otherwise). Steps whose condition does not match the answers are `Skipped`.
- `POST /api/parishes/{parish}/workflow-runs/{run}/steps` — `Completed` or `Declined` (reason required) for the *current* step only, by an actor holding that step's permission in the selected capacity. Completing the last applicable step closes the run as `Completed`; declining ends it as `Declined`.
- `POST …/{run}/actions` (process owner, reason required): `pause` (InProgress→Paused), `resume`, `cancel` (InProgress/Paused→Cancelled), `reopen` (Completed/Declined/Cancelled→InProgress in a new cycle, redoing the step where the run ended — not a restored approval).
- `GET …/{run}`, `GET …/{run}/history` (immutable rows with actor, selected appointment, cycle and reason), `GET /workflow-runs?definitionId=&status=` (process owner), `GET /workflow-runs/worklist` (runs whose current step the caller may act on now; pages can be short — follow the cursor).
- Every write fences the parish root, the definition (so a mode change cannot race a step) and the run ETag; exact retries replay; stale versions fail with `write_conflict`.

## Not delivered / proposed only
A step result is a recorded decision only: it never performs or proves a sacrament, signature, payment, document release or appointment, and no dedicated clergy/finance decision is replaced. Not delivered: a separate publisher role or second approver (the process owner publishes), member/guest self-start, attachments/file fields, multilingual labels and preview rendering, parallel approvals, return-for-information/resubmission (WF49-T90/T91), deadlines, reminders and escalation, transfer of responsibility, notifications for transitions, version migration of active runs, diocesan template adaptation, assignee-existence checks at publish (no grant enumeration), and impact review of linked resources/money on cancel. Workflow ownership is not a priest appointment duty, so process owners currently use an explicit parish grant. Local tests do not prove live Cosmos behavior.
