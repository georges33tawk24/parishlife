## MFA issue actually reproduced and fixed locally

`MfaSecurityService.BeginAsync` read `mfaEnrollment` before checking the operation receipt. A competing duplicate could commit its enrollment/receipt after that read; the replay path then validated a stale null/older enrollment instead of the committed one. The local fix rereads the current saved enrollment on replay and retains exact ID/account/Pending/security-stamp/expiry checks.

`MfaEnrollmentReplayTests` inserts a competing real-store enrollment at that exact boundary without timing/sleep assumptions. It failed before the change and passes afterward, returning only the committed enrollment/key with a single operation receipt. Existing one-time completion/recovery-code issuance was preserved.

## Unresolved findings from focused source review

These are concrete code-review findings for regression/repair, **not claims that all were reproduced in a live service or that the 24k-line update received a complete audit**. No other implementation was changed during this handover.

1. **Request-file stale payload/new ETag can overwrite a concurrent case change.** [EvidenceService](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Files/EvidenceService.cs#L29) reads/checks an initial case payload, but upload [line 85](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Files/EvidenceService.cs#L85) pairs that payload with a newly fetched request version. A close/triage completed between those reads can be overwritten. Retain the original conditional version and recheck after conflict; add deterministic concurrent-close tests.
2. **Request-file retries are not bound to actual bytes.** The [operation input](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Files/EvidenceService.cs#L49) includes length/metadata but no digest. If blob storage succeeds and metadata fails, a same-operation retry with different same-length content can calculate a new digest while reusing the old [existing staged blob](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Files/EvidenceService.cs#L87). Durably bind/check digest and verify staged bytes; test that failure/retry window.
3. **Applicant file paths skip the office status/entitlement gate.** [CaseAsync's applicant branch](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Files/EvidenceService.cs#L34) checks personal account eligibility then returns, while the office branch checks requests permission/module. Review the intended suspension/closure/lapse policy, block prohibited new writes and preserve specifically authorized history/cleanup. Do not infer a new retention policy.
4. **Registration eligibility is not revalidated after event edits.** Configure an eligible draft ParishActivity, change the calendar draft into a private/ineligible event, then confirm/open registration. [Opening](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Registrations/RegistrationService.cs#L135) only checks future/Confirmed and subsequent office registration paths omit the initial kind/visibility guard. Protect source ownership and recheck at opening/decisions; add this transition regression.
5. **Door/cashier roles cannot obtain versions needed for their narrow writes.** Registration [detail/list reads](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Registrations/RegistrationService.cs#L247) require registrations.manage, while presence/receipt writes require their own narrower duties plus a Version. Present roster lacks not-yet-arrived participants/versions; tests obtain versions directly from storage. Add purpose-limited versioned projections and real HTTP tests without granting broad private registration access.
6. **Submission does not pin the form actually answered.** Office/member submission DTOs omit the viewed FormVersionId; the service loads and pins the [latest form](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Registrations/RegistrationService.cs#L215). Answers entered against v1 can silently become v2 after a label change retaining keys/types. Require the actual viewed version and an explicit stale-form review conflict. Applicant-readable safe form access is also incomplete.
7. **Required notifications remain best-effort across partitions.** [Request mutations](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Requests/RequestService.cs#L212) commit before notification creation; a crash/failure between them loses the notice, while operation replay returns before repairing it. [NotificationService](https://github.com/georges33tawk24/parishlife/blob/a4cb405899bb6fde0e9c186dde1f4bb1ee1be24f/ParishLife.Api/Services/Communications/NotificationService.cs#L20) explicitly calls this best effort. Implement durable source outbox/relay/retry with dedupe, current target authorization and generic private previews; test interruption recovery.
