# ParishLife backend implementation status — first slice

Prepared 3 November 2026. Application code is now being implemented in `C:/Users/User/source/repos/ParishLife`. The original investigation, updated architecture/workflow documents and old reference repositories remain intact.

**This is production-intended code, not the finished whole ParishLife system.** The current catalogue has 137 baseline capabilities plus 12 subscription journeys. All 149 are tracked below. A source/architecture proposal is not counted as replacement implementation, and a local passing scenario is not treated as actual Cosmos service validation.

## Implemented first slice

- Seven solution projects: Api, Application, Domain, Infrastructure, unit checks, integration checks and explicit Maintenance CLI. Existing API project retained in its existing location; the weather demo was replaced.
- Controller → application service → purpose-specific repository; Domain has no ASP.NET/EF/Azure dependency.
- Cosmos for NoSQL only: explicit SDK batches for protected writes, EF Core Cosmos for immutable plan catalogue documents. No Pomelo, relational database/migrations, Blazor, microservices or Bicep dependency.
- Email registration through Identity managers/custom Cosmos stores; unique normalized alias ownership, resumable pending activation and manual contact verification. No parish Person or appointment is created by signup.
- Secure cookies, antiforgery on every unsafe request, lockout, durable sessions/security-stamp checks, password change and TOTP challenge login. Platform operators require current operator status plus MFA. Authenticator secrets are protected per account through Data Protection.
- Independent parish and archdiocese setup/verification. Parish tenant identity is permanent; association is optional. Actual clergy qualification/appointment workflows have not been implemented or invented.
- Controlling parish owner manages basic explicit account grants. Association acceptance creates neither private access nor a billing transfer. Association epochs invalidate ended delegations and prevent old grants reviving on rejoin.
- Manually published immutable plan terms, own invoices, operator-confirmed cash receipts/partial payments, scoped paper-reference guard and auditable operation replay. Customers cannot self-confirm cash.
- Paid invoice activation through durable due work, guarded leases and idempotent tenant coverage commits. Pending activation is visible; overlapping paid periods require review. Billing and entitlement are coordinated across their actual partition boundary.
- Office entitlement gates basic parish people create/read/page/archive/restore. Explicit response projections and protected tenant/query-bound cursors are used.
- Typed configuration validation, ProblemDetails, no-store API responses, liveness and protected metadata readiness, private Blob/Key Vault Data Protection and a manual Azure resource contract.

## Production setup and limits

Create production Azure resources using [the manual guide](../azure-manual-setup/production.md) and [container manifest](../cosmos/containers.json). Runtime does not provision resources, migrate existing data or seed privileged accounts. [Initial setup](../operations/initial-setup.md) describes explicit operator/contact verification and cash flows. Operator maintenance uses the same production key ring as the hosted API but authenticates with the operator's authorized Azure credentials.

Not yet implemented: calendar/resource allocation, ministries, sacramental workflows and signatures, document/file release, households/membership/imports/merge, parish accounting/Office ledger, confidential care, messaging/delivery, rich reporting, custom workflows and the other catalogue entries below. Central multi-parish purchasing and payer transfer are also unfinished. Cash subscription receipts do not implement parish donations/accounting or the complete refund/renewal lifecycle.

No Azure resource was provisioned and no production data was written by this coding session. No destructive/live database checks were run. The frontend was not changed. Actual Cosmos transactions/queries, managed identity/network access, deployed password/session/MFA persistence, Blob/Key Vault access and restore consistency still need verification against the configured infrastructure. Local HTTP scenarios use isolated repository/authentication doubles. The local installed runtime was 10.0.12; production deployment needs serviced .NET 10 with 10.0.13 security fixes or newer.
