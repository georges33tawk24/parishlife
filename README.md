# ParishLife

ParishLife is a bilingual parish administration application served by a small Python 3.11+ HTTP server. The browser uses ES modules without a build step. SQLite is the authoritative store; the browser holds only the current view model. Start the application with `server.py`, not the older static `.claude/serve.py` script.

## Start locally

```powershell
cd 'C:\Users\User\Downloads\parishlife-master\parishlife-master'
$parishPython = 'C:\Users\User\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $parishPython server.py 4399
```

Open `http://127.0.0.1:4399` for the public homepage, then choose **Members portal** (`index.html`) and sign in with an existing account. If port 4399 is already occupied by an older run, stop that terminal with Ctrl+C and start it again so the updated server code loads. On this machine, `python` and `py -3` do not resolve to an installed interpreter; the bundled executable above works. On a machine with Python 3.11+ installed, `python server.py 4399` is equivalent.

To create an additional account, run `& $parishPython server.py --create-user bishop --role bishop --name "Bishop"`, or use `--role priest|secretary|treasurer|leader --parish p-elias` as appropriate. A regular parish member or volunteer uses `& $parishPython server.py --create-user carla --role member --name "Carla Abou Jaoude" --person-id p6 --parish p-elias`. The person must have an active record in the assigned parish; they do not need to belong to a ministry group. Group membership comes from that person's group roster, not from the account role. The former volunteer-only role and its sign-in are disabled on startup; create a member account for anyone who still needs access. Each account command prompts for a password of at least 12 characters. A bishop has diocesan oversight and management through Administration, including parish creation, scoped appointments, clergy titles, bundles and certificate acceptance. Existing local operator commands remain available; new appointments can also be managed in the application within the actor's authority. An unassigned priest cannot open parish records. Use `--person-id` when the account corresponds to a person in the parish. The server binds to localhost.

Complaint access is case-specific: the submitter selects independent reviewers. A role by itself does not expose complaints, their counts or status. Selected reviewers receive the permissions needed for those cases; anonymous submitter identities remain hidden. The application checks named conflicts before accepting reviewer selections and when reviewing. Existing operator permission grants control reviewer capabilities, but do not replace case access. Ministry leaders no longer receive a general complaints feed.

Leaders can save group messaging automation and rule configurations. They are records for planning; no timed runner or external message delivery is connected. Staff can send in-app messages to account holders and publish parish or group updates; email, WhatsApp, SMS, and emergency broadcasts are not delivered by this installation.

The first start creates `var/parishlife.sqlite3` from `backend/seed.json`. Saint Elias contains sample data; the other sample parishes start with independent empty records. The `var/` directory is ignored by Git. Back up the database file with the server stopped or with SQLite's backup facility. The browser's Data snapshot export is a review artifact, not a database restore path.

## Architecture

- `server.py`: same-origin HTTP API, password-authenticated sessions, CSRF token, parish assignment checks, collection write permissions, SQLite schema, migrations, register workflow, and audit trail.
- `backend/seed.json`: initial sample state.
- `backend/workspace.py`, `workspace-schema.json`, `account_services.py`, `profile_services.py`, `ministry.py`, `guest_links.py` and `guest_delivery.py`: additive account, authority, membership, profile review and guest request services. Matching Worker modules live under `cloudflare/src/`.
- `assets/collection-ui.js`, `assets/theme.js`, `assets/auth.js`: shared calendar/pagination controls, personal appearance and account entry screens.
- `assets/api.js`: authenticated session and parish API client.
- `assets/persist.js`: hydrates the browser view model from SQLite and saves changed collections with an optimistic revision check.
- `assets/data.js`: shape and initial values of the frontend view model.
- `assets/app.js`, `assets/store.js`: shell, router, signed-in role, parish selection, and navigation.
- `assets/views/`: screens. `assets/views/people.js` covers people and households; `assets/views/oversight.js` is the separate bishop view; `assets/views/records.js` covers requests, preparation, register entries, certificates, and anniversaries; `assets/views/notes.js` covers private pastoral notes and tasks; `assets/views/parish.js` covers calendar, Services & Activities, groups, registration, and check-in.
- `assets/planning.js`: selects and copies service plans and templates without sharing their order-of-service arrays.
- `assets/print.js`: prints a sheet from a hidden frame (no new tab), saves files, and turns the certificate drawing into a PNG.
- `assets/schedules.js`: the "Print my week" sheet and the clergy Mass schedule.
- `assets/crud.js`, `assets/flows.js`, `assets/actions.js`: shared record forms and user actions.
- `assets/parishlife.css`, `assets/app.css`, `assets/components.js`, `assets/ui.js`: design system and controls.

The API resolves authority from stored assignments and scoped grants, never a role submitted by the browser. Bishops and diocesan administrators are limited to their diocese; parish administrators are limited to their parish. Clergy appointments may span several parishes, each with a separate person link. Only bishops change clergy titles. A bishop or super administrator can explicitly delegate clergy appointments to a diocesan administrator. Private pastoral notes are author-only unless their author shares them with the current parish priests; administrators do not inherit access. Finance administration is available to Super Admins, bishops, Archdiocese Admins, Parish Admins and priests; treasurers retain their existing access. Finance viewing can also be delegated without editing or certificate-signing authority. Register approval and signature actions remain with priests.

Normal members use a separate server projection and cannot request the general parish state endpoint. Their portal shows only their roster memberships, related meetings, own attendance, permitted calendar events, authorized posts/resources, personal notes, communications, commitments, profile, and concerns. The member `role` is an account access tier; a ministry roster entry remains a membership and grants no leadership action. Linked staff accounts other than secretaries can open **My parish life** from the account menu to use their personal member pages alongside their scoped staff tools. Staff publishing is scoped to their own ministry or the parish office. Member notes are stored per account outside the shared parish state; leaders, clergy, and parish administrators do not automatically receive them. Profile changes enter an office review queue rather than editing the official person record directly. Internal messages and announcements are distinct. In-system notifications cover published updates, meeting changes, attendance, replies, volunteer confirmations, profile reviews, and identified concern updates, with per-account preferences and read controls. Upcoming meeting reminders are generated once when the member opens the portal within one day of a meeting; no background scheduler is configured. Email notification preferences are stored but no external email delivery is configured. New attachments accept PDF, PNG, JPEG, or text up to 1 MB.

Concerns have identified or anonymous submission, status history, public responses, optional evidence, and follow-up from the submitter's Concern page. Anonymous cases store no account identity in the case or restricted complaint audit; their IDs are kept in the submitter's private account data to show status without a code. Operators with direct database access can still correlate that data, and server infrastructure can leave technical metadata. Complaint cases and audit records are separate from the general parish state and activity feed. Sensitive and newly added categories require `ViewSensitive` in addition to `Review`; a reviewer needs `ViewIdentity` to see an identified submitter's name and phone. Anonymous cases submitted before this change cannot be linked to an account automatically.

## Main workflows

People belong to a parish and may be members of one household. New households reuse several existing people in one selection, record a shared address once, and can designate a household contact. Surname matches are suggestions to review; records are never merged automatically. Historic family/branch relationships remain in storage but are not editable concepts in the household interface. Group membership changes from a person's profile require review and confirmation. The printed people directory includes only people who explicitly opt in; it shows English and Arabic names, household, town, and phone. The offering-envelope identifier is optional and belongs to a household, not each member; it connects counted gifts to that household without marking every member as a donor. It is not auto-generated. The inter-parish person transfer workflow has been removed. Names are entered as supplied, with English first, without automatic transliteration or a Preferred Name field. The Family tab draws the household from each member's relationship and its "Related to" person: parents above, couples on a ring, children under their own parents, and a marker where brothers' and sisters' parents are not recorded. Changing the household head keeps everyone's relationships (the old head becomes, for example, the new head's spouse).

A family begins a sacrament by asking the parish office to enter a request. The secretary may review it, while the priest can accept or decline it directly without waiting for that review. Accepted requests move to Preparation, where the office records the date and checks the requirements. Only completed preparation can move to the scheduled celebration. After the celebration, the office submits the entry for priest review; priest approval assigns its official register number. The request reference and full history remain linked to the same record. Requests is the searchable action queue and completed request history. The Sacraments page has two tabs, Preparation and Anniversaries; there is no separate register list — an approved entry is reached from Requests or from the person's Sacraments tab, and "Export register (CSV)" downloads every approved entry. Certificate requests can be linked to a planned sacrament and wait for its official entry, or go directly to clergy review when one already exists. Certificate issuance is a separate clergy action. The register-correction screens were removed from the interface (the server's correction actions and any stored corrections are kept). Cancelling preparation or declining a request keeps its history. Each record shows its progress as numbered steps with the single next step and who takes it; every finished step says the date and time it happened, the current one says since when it has waited, and the celebration step shows the planned date and time. The office sets a celebration time beside its date (in Preparation and in Edit details, half-hour steps); the parishioner sees it on their request page and in the "date set" notification. An approved entry or certificate appears as a small A4 preview: click it for full size in Arabic, English or bilingual, print it, or download it as a PDF (through the print dialog), a PNG or an SVG — all drawn from the same vector sheet.

Parishioners can also ask online. In the member portal, **My requests** (`assets/views/member-requests.js`) lets a member request a baptism, First Communion, confirmation, marriage, funeral or certificate for themselves or someone in their household, book a hall, room or outdoor space (with the times already taken shown as they choose), or ask for anything else in their own words (a house blessing, a Mass intention, a visit to someone who is sick). For a baptism, the request can also be for a child who is not registered yet. Signed-in members retain their detailed request forms, while the public parish page also accepts guest requests without sign-in, and the parish website editor has a matching section for its introduction. Online requests wait in their own table (`member_requests`), outside the parish state, so a parishioner never edits the record the office works on. The office reviews them in Requests (`assets/views/online-requests.js`): accepting one creates the usual sacrament or certificate entry, which a secretary sends to the priest and a priest can accept for preparation directly. A child gets a new person record or is matched to an existing one, and can join the requester's household. A certificate is linked to the official entry when one exists. Declining requires a message to the parishioner. The parishioner follows each step on their request page, with a notification when the request is accepted, declined, dated, prepared, recorded, cancelled or ready to collect. They can withdraw a request until the office has handled it. The reasons the office gives for declining, rejecting or cancelling are shown to the parishioner, and those dialogs say so.

A booking that the office accepts becomes a reservation (`RES-…`) in Reservations: a secretary sends it to the priest, a priest confirms it directly, and confirming, refusing (with a reason the parishioner reads) or removing it notifies the parishioner. A general request is accepted and then marked as done, or declined with a message.

Anyone aged 13 or older can open an account with separate first and last names, date of birth, email and/or phone, and a confirmed password. Sign-in explicitly selects Username, Email or Phone, preserving existing credentials without presenting a username as an email address. Sign-up has no parish selector and creates no person or ministry roster record. Complete Profile is skippable: users can follow several parishes, choose a primary parish, and independently request office-approved membership. The office links an existing person record after identity review. Office-created people can receive an invitation link to continue their account; invitation delivery is manual until outbound services are configured. My parish records shows existing information and submits proposed changes for approval under Requests → Profile corrections. Account contact information and official parish records remain separate from login identities.

Google, Apple, Microsoft, email/SMS verification and authenticator setup are clearly unavailable in the current installation. No external verification, identity linking or MFA success is simulated. These need provider credentials and delivery/verification implementation before production activation. Contacts created in this preview remain unverified.

Pastoral notes are reference information; tasks have actionable status, assignee, and due date. They are private to their author by default; an author may share an item with the parish priests. Calendar events can be public, visible to selected groups, or restricted to parish office and clergy. Masses can have assigned priests and a clergy-only printable schedule. "Print my schedule" (calendar and dashboard) and "Priest schedule" open a dialog — a week or period to choose, what to include, a live count — and print a laid-out A4 sheet without opening a new tab. Service plans use an explicit Save action, chronological item times, and a total duration. Group attendance is recorded per member and meeting in a matrix, with retained former-member history; individual Mass attendance is not collected. Formation means the group's training or faith-development milestones. Registration forms link to explicit eligible events; when the event is not in the calendar yet, it can be described inside the new-form drawer (its room is checked against the calendar, room bookings and maintenance blocks) and is created together with the form; check-in is a separate arrival record for registrants of the selected event. Existing unlinked forms and check-in records are preserved but must be linked or migrated before use in the new event-based flow. Consent fields stay in person data. Anniversaries derive from registered baptism, chrismation, first Communion, and marriage entries, with earlier marriage reminders labelled legacy. The volunteer rota is one row of team columns that scrolls sideways, with full-size cards; drag and drop works across it. Facilities: each room's Availability opens a month calendar to pick any day, the day's bookings and free slots on a 07:00–23:00 strip (with set-up time), and a Book button on every free slot (earlier days are shown for reference and cannot be booked); each room card has its own "Block for maintenance", which lists the bookings that fall inside the chosen dates; Equipment has a search and an All / Available now / On loan / Needs attention filter. In Forms & workflows, each step of a task shows when it was done, clicking a task opens it, finishing its last step closes it, a task can be cancelled (with Undo), and each workflow is paused or resumed on its own. Record history shows times in the viewer's local time.

### Colours

Each user chooses a dashboard preset or custom primary color and light/dark mode in My account. The setting is stored against the account and applies across their parishes. Public pages use one shared site theme. Existing `PARISH.theme` values are retained for compatibility but do not override the public theme or personal dashboard preference. Certificates and printed pages keep their print styling.

## Database migration and operating limits

`init_db()` creates or updates the SQLite schema on startup. Existing stored parish state is migrated to preserve historic household relationships, add pastoral task fields, reusable event and service templates, event visibility and priest assignments, event-linked registration/check-in containers, service plans, meeting attendance maps, and register history/revision metadata. The normalized relationship tables are rebuilt with parish-scoped foreign keys. The old transfer collection and Preferred Name field are removed from migrated state. Back up an existing database before starting a newer version.

This is a local application baseline. Official register numbering, certificate templates, retention rules, and external parish verification need archdiocese approval before live administrative use. UI exports and communication controls do not constitute delivery integrations. Scoped administration is covered by shared Python/Worker HTTP tests, concurrency checks and browser verification; see [administration](docs/administration.md). The older broader regression suite still has pre-existing failures.

## Public website design

The site's address (`http://127.0.0.1:4399/`, the same page as `public.html`) opens the homepage: a night valley where every gold light is a parish, this week's celebrations, a map of Lebanon with the parish directory, requests to the parish office, Mass times, announcements and stories. A Super Admin edits its wording, announcement, stories and sections under **Administration → Homepage**; everything else comes from each parish's Website content, public profile, calendar and announcements. See [homepage design](docs/homepage-design.md). The homepage leads to the public parish pages; **Members portal** in the header leads to the sign-in for parishioners and parish staff, and the sign-in screen links back to the website. The directory offers search, town/diocese/rite filters, sorting and an optional nearest-first order from the visitor's location; the map is drawn locally and needs no map service. Parish pages share the homepage's design: without a photograph the valley flies in to the parish's own light, and each section (history, Mass times, calendar, ministries and clergy, requests, news, photographs, visiting information with the parish on the map, nearby parishes) appears only when the parish has published it. The calendar has a month view, a coming-up list, search and an add-to-calendar file for each event, and a dedicated full-calendar page. **Member portal → Website content** manages the published sections. See [design and verification notes](docs/public-site-design.md) and the [reference-site audit](docs/reference-design-audit.md).

## Office workspace update

Restart the Python application server after updating these files, then refresh the browser. Startup adds the office ledger and attachment requirement field to existing parish databases. No data reset or reseeding is needed.

- **Services & Activities** is the new label for Service planning; **Notes & Tasks** is the new label for Pastoral notes. The clergy workspace displays notes and tasks beside each other on wide screens, with one search/filter/sort toolbar.
- **Anniversaries** supports a combined table or tables grouped by sacrament, remembered per account in the browser.
- **Request documents** are available on each service request and sacramental request. Upload PDF/JPG/PNG files against an individual requirement, replace or remove them, or explicitly record a paper/in-person receipt. Required items determine document completeness independently of priest approval. Completed or closed requests retain read-only attachments. Uploads and receipt changes are parish-scoped, revision checked and audited.
- **Households** has checkboxes in cards and table views, Export selected households, and Export filtered households. Household details and the Family tab on person profiles can export the current household directly, including members and relationships. CSV files preserve Arabic text.
- **Registrations & Payments** uses one participant form for place status, applicable consent, explicit transport choices and received payments. Reserved places may await consent; final confirmation and new check-ins require consent only where event settings require it. Unknown birth dates require review when parental consent is enabled. Configure transport options and charges on the registration form. Payments use the event currency, record amount/method/date/reference, and preserve previous entries. Once participants exist, the event and currency cannot change. Already recorded participant fees remain attached to their registration.
- **Secretary access** contains only dashboard, people, households, sacraments, requests, calendar, Services & Activities, groups, volunteers, registrations, check-in, facilities, reservations and Office Expenses. Group pages show members/contacts, meetings and resources. Contextual in-app messaging remains available. Administration, standalone communications, and personal member routes are excluded from this workspace.
- **Office Expenses** is available to the secretary and parish priest. It records allowances, purchases and an optional initial opening balance, with CRUD actions, receipt attachments, internal printed vouchers and monthly summaries. USD and LBP have independent running balances. Earlier balances carry forward automatically; enter an opening balance only once per currency. These records are stored once in `OFFICE_LEDGER` and are not duplicated into parish Finance expenses. Changes are audited, including deleted records.

See [administration verification](docs/administration.md#verification) for current tests and the recorded limitations of the older regression suite.

See [account and permission workflows](docs/account-workflows.md) for the source changes and external integration boundaries. The working branch is `colin`; changing source files does not itself publish the site or update the Cloudflare database.

**Administration → Edit public parish profile** manages visiting information, office contacts, Mass/confession times, accessibility, coordinates and gallery links. ## Scoped administration and optional secretaries

See [administration, provisioning, migration and verification](docs/administration.md).

Super Admins administer the whole system. Bishops appoint Archdiocese Admins;
priests and authorized higher administrators appoint Parish Admins. Parish Admins
manage parish office work and secretaries without receiving clergy authority.
Secretary appointments are optional during parish creation and afterward.

Provision developer access with an explicitly chosen account and a securely
prompted password; no default privileged password or demo bootstrap is available:

```powershell
& $parishPython server.py --bootstrap-super-admin developer-colin --name "Colin"
```

Both backends enforce scoped access, immediate role revocation, audit history,
current-password checks for Super Admin changes, and last-Super-Admin protection.
The interface includes system/archdiocese/parish appointment scopes, optional
secretary selection and an administration workflow before the first parish exists.

Verification includes 49 shared HTTP tests against each backend, D1 concurrency
checks and desktop/mobile browser workflows. The broader suite's older failures
remain tracked separately. No production deployment or live account modification
was performed. Restart the local server to load the changes and back up an existing
database before deploying an update.
