# ParishLife

ParishLife is a bilingual parish administration application served by a small Python 3.11+ HTTP server. The browser uses ES modules without a build step. SQLite is the authoritative store; the browser holds only the current view model. Start the application with `server.py`, not the older static `.claude/serve.py` script.

## Start locally

```powershell
cd 'C:\Users\User\Downloads\parishlife-master\parishlife-master'
$parishPython = 'C:\Users\User\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
& $parishPython server.py 4399
```

Open `http://127.0.0.1:4399` for the public homepage, then choose **Members portal** (`index.html`) and sign in with an existing account. If port 4399 is already occupied by an older run, stop that terminal with Ctrl+C and start it again so the updated server code loads. On this machine, `python` and `py -3` do not resolve to an installed interpreter; the bundled executable above works. On a machine with Python 3.11+ installed, `python server.py 4399` is equivalent.

To create an additional account, run `& $parishPython server.py --create-user bishop --role bishop --name "Bishop"`, or use `--role priest|secretary|treasurer|leader --parish p-elias` as appropriate. A regular parish member or volunteer uses `& $parishPython server.py --create-user carla --role member --name "Carla Abou Jaoude" --person-id p6 --parish p-elias`. The person must have an active record in the assigned parish; they do not need to belong to a ministry group. Group membership comes from that person's group roster, not from the account role. The former volunteer-only role and its sign-in are disabled on startup; create a member account for anyone who still needs access. Each account command prompts for a password of at least 12 characters. A bishop account has a read-only oversight screen with parish filters and drill-downs, and manages its diocese (appointments, clergy titles, document acceptance, plan arrangements) in **Administration**. Parish assignment can also be an operator action on the local machine, for example `& $parishPython server.py --assign-user fr-antoine --parish p-elias`; in Administration a priest's parish access follows their clergy service assignment. An unassigned priest cannot open parish records. Use `--person-id` when the account corresponds to a person in the parish. The server binds to localhost.

Two switches exist for **local demonstration only**. `server.py --demo-super-admin` creates (or restores) the account `super-admin` with the publicly known password `123456789` and an active super-admin role; never use it on a server other people can reach. `server.py --dev-outbox` prints verification codes in the console, labelled as not sent, instead of delivering them. Neither is enabled by default, and the Cloudflare deployment has no equivalent of the first: a production super admin is created with `node cloudflare/tools/accounts.mjs create-super-admin <username> --name "…"`, which generates a strong password and refuses the demonstration one (see [cloudflare/README.md](cloudflare/README.md)).

Complaint review is never implied by priest, secretary, leader, or member access. An operator must explicitly grant it, for example `& $parishPython server.py --grant-complaints safeguarding --parish p-elias --complaint-permission Review --complaint-permission Respond --complaint-permission ViewSensitive`. Add `Resolve` to close cases and `ViewIdentity` only when the reviewer needs identified submitter details. A named reviewer is excluded from cases that list them among the people involved. Choose another authorized reviewer for those cases.

Ministry leaders can see read-only, non-sensitive complaints linked to groups they lead in **Complaints received**. This view excludes cases involving the leader, does not reveal submitter identity or attachments, and logs each access. Review, responses, and sensitive cases still require explicit reviewer permissions.

Leaders can save group messaging automation and rule configurations. They are records for planning; no timed runner or external message delivery is connected. Staff can send in-app messages to account holders and publish parish or group updates; email, WhatsApp, SMS, and emergency broadcasts are not delivered by this installation.

The first start creates `var/parishlife.sqlite3` from `backend/seed.json`. Saint Elias contains sample data; the other sample parishes start with independent empty records. The `var/` directory is ignored by Git. Back up the database file with the server stopped or with SQLite's backup facility. The browser's Data snapshot export is a review artifact, not a database restore path.

## Cloudflare

The same application also runs on Cloudflare Workers with a Cloudflare D1 database, without `server.py`; see [cloudflare/README.md](cloudflare/README.md).

## Architecture

- `server.py`: same-origin HTTP API, password-authenticated sessions, CSRF token, parish assignment checks, collection write permissions, SQLite schema, migrations, register workflow, and audit trail.
- `backend/seed.json`: initial sample state.
- `assets/api.js`: authenticated session and parish API client.
- `assets/persist.js`: hydrates the browser view model from SQLite and saves changed collections with an optimistic revision check.
- `assets/data.js`: shape and initial values of the frontend view model.
- `assets/app.js`, `assets/store.js`: shell, router, signed-in role, parish selection, and navigation.
- `assets/views/`: screens. `assets/views/people.js` covers people and households; `assets/views/oversight.js` is the separate bishop view; `assets/views/records.js` covers requests, preparation, register entries, certificates, and anniversaries; `assets/views/notes.js` covers private pastoral notes and tasks; `assets/views/parish.js` covers calendar, service planning, groups, registration, and check-in.
- `assets/planning.js`: selects and copies service plans and templates without sharing their order-of-service arrays.
- `assets/print.js`: prints a sheet from a hidden frame (no new tab), saves files, and turns the certificate drawing into a PNG.
- `assets/schedules.js`: the "Print my week" sheet and the clergy Mass schedule.
- `assets/crud.js`, `assets/flows.js`, `assets/actions.js`: shared record forms and user actions.
- `assets/parishlife.css`, `assets/app.css`, `assets/components.js`, `assets/ui.js`: design system and controls.

The API never trusts the selected parish or role from the browser. Access comes from role assignments scoped to the whole system, one diocese or one parish, each with a permission template and per-appointment additions and removals; the parish workspace checks those permissions on every read and write. The bishop's oversight screen is a read-only projection and cannot load or mutate parish working state. A pastoral note is sent only to its author, or, when the author shared it, to the priests serving that parish now; giving data is limited to clergy and treasurers. Register approval, issuance, and correction approval are handled through dedicated API actions rather than ordinary record saves.

Normal members use a separate server projection and cannot request the general parish state endpoint. Their portal shows only their roster memberships, related meetings, own attendance, permitted calendar events, authorized posts/resources, personal notes, communications, commitments, profile, and concerns. The member `role` is an account access tier; a ministry roster entry remains a membership and grants no leadership action. Linked staff accounts can open **My parish life** from the account menu to use their personal member pages alongside their scoped staff tools. Staff publishing is scoped to their own ministry or the parish office. Member notes are stored per account outside the shared parish state; leaders, clergy, and parish administrators do not automatically receive them. Profile changes enter an office review queue rather than editing the official person record directly. Internal messages and announcements are distinct. In-system notifications cover published updates, meeting changes, attendance, replies, volunteer confirmations, profile reviews, and identified concern updates, with per-account preferences and read controls. Upcoming meeting reminders are generated once when the member opens the portal within one day of a meeting; no background scheduler is configured. Email notification preferences are stored but no external email delivery is configured. New attachments accept PDF, PNG, JPEG, or text up to 1 MB.

Concerns have identified or anonymous submission, status history, public responses, optional evidence, and follow-up from the submitter's Concern page. Anonymous cases store no account identity in the case or restricted complaint audit; their IDs are kept in the submitter's private account data to show status without a code. Operators with direct database access can still correlate that data, and server infrastructure can leave technical metadata. Complaint cases and audit records are separate from the general parish state and activity feed. Sensitive and newly added categories require `ViewSensitive` in addition to `Review`; a reviewer needs `ViewIdentity` to see an identified submitter's name and phone. Anonymous cases submitted before this change cannot be linked to an account automatically.

## Main workflows

People belong to a parish and may be members of one household. New households reuse several existing people in one selection, record a shared address once, and can designate a household contact. Surname matches are suggestions to review; records are never merged automatically. Historic family/branch relationships remain in storage but are not editable concepts in the household interface. Group membership changes from a person's profile require review and confirmation. The printed people directory includes only people who explicitly opt in; it shows English and Arabic names, household, town, and phone. The offering-envelope identifier is optional and belongs to a household, not each member; it connects counted gifts to that household without marking every member as a donor. It is not auto-generated. The inter-parish person transfer workflow has been removed. Names are entered as supplied, with English first, without automatic transliteration or a Preferred Name field. The Family tab draws the household from each member's relationship and its "Related to" person: parents above, couples on a ring, children under their own parents, and a marker where brothers' and sisters' parents are not recorded. Changing the household head keeps everyone's relationships (the old head becomes, for example, the new head's spouse).

A family begins a sacrament by asking the parish office to enter a request. The secretary may review it, while the priest can accept or decline it directly without waiting for that review. Accepted requests move to Preparation, where the office records the date and checks the requirements. Only completed preparation can move to the scheduled celebration. After the celebration, the office submits the entry for priest review; priest approval assigns its official register number. The request reference and full history remain linked to the same record. Requests is the searchable action queue and completed request history. The Sacraments page has two tabs, Preparation and Anniversaries; there is no separate register list — an approved entry is reached from Requests or from the person's Sacraments tab, and "Export register (CSV)" downloads every approved entry. Certificate requests can be linked to a planned sacrament and wait for its official entry, or go directly to clergy review when one already exists. Certificate issuance is a separate clergy action. The register-correction screens were removed from the interface (the server's correction actions and any stored corrections are kept). Cancelling preparation or declining a request keeps its history. Each record shows its progress as numbered steps with the single next step and who takes it; every finished step says the date and time it happened, the current one says since when it has waited, and the celebration step shows the planned date and time. The office sets a celebration time beside its date (in Preparation and in Edit details, half-hour steps); the parishioner sees it on their request page and in the "date set" notification. An approved entry or certificate appears as a small A4 preview: click it for full size in Arabic, English or bilingual, print it, or download it as a PDF (through the print dialog), a PNG or an SVG — all drawn from the same vector sheet.

Parishioners can also ask online. In the member portal, **My requests** (`assets/views/member-requests.js`) lets a member request a baptism, First Communion, confirmation, marriage, funeral or certificate for themselves or someone in their household, book a hall, room or outdoor space (with the times already taken shown as they choose), or ask for anything else in their own words (a house blessing, a Mass intention, a visit to someone who is sick). For a baptism, the request can also be for a child who is not registered yet. The parish page links straight to each request through sign-in, and the parish website editor has a matching section for its introduction. Online requests wait in their own table (`member_requests`), outside the parish state, so a parishioner never edits the record the office works on. The office reviews them in Requests (`assets/views/online-requests.js`): accepting one creates the usual sacrament or certificate entry, which a secretary sends to the priest and a priest can accept for preparation directly. A child gets a new person record or is matched to an existing one, and can join the requester's household. A certificate is linked to the official entry when one exists. Declining requires a message to the parishioner. The parishioner follows each step on their request page, with a notification when the request is accepted, declined, dated, prepared, recorded, cancelled or ready to collect. They can withdraw a request until the office has handled it. The reasons the office gives for declining, rejecting or cancelling are shown to the parishioner, and those dialogs say so.

A booking that the office accepts becomes a reservation (`RES-…`) in Reservations: a secretary sends it to the priest, a priest confirms it directly, and confirming, refusing (with a reason the parishioner reads) or removing it notifies the parishioner. A general request is accepted and then marked as done, or declined with a message.

Anyone 13 or older can open an account from the sign-in screen (**Create an account**) with a first and last name, an email address and/or a phone number, a date of birth and a password; no parish is chosen at registration, and the account starts with no parish role. Sign-in has Email, Phone number and Username tabs. Phone numbers sign in however they are typed (`03 123 456`, `+961 3 123 456`, `00961…`, Arabic digits); Lebanon is assumed unless another country code is given. From **My parishes** an account follows parishes, asks to join one as a member (the office links the request to an existing person record or creates one, or declines with a reason), chooses a primary parish and withdraws or stops following. The office can also invite people already on record. Following, membership, ministry leadership and staff roles are separate relationships, and one account can hold several of them in several parishes. A forgotten password of an account without a staff role can be reset by the priest or secretary from the person's **Online account** panel, which shows a temporary password to read over the phone; everyone changes their own password from **My account**, which also holds contacts and their verification, two-step verification (authenticator app with recovery codes) and linked sign-in providers. Sign-ups are limited to 30 an hour, repeated sign-in failures for one name to 10 per 15 minutes, and the forms carry a hidden field that only robots fill in. Verification codes, invitations and tracking links are sent only through a configured delivery service, and Google, Apple and Microsoft sign-in stay unavailable until configured (see **Configuration** below); the screens say which applies.

Pastoral notes are reference information; tasks have actionable status, assignee, and due date. A note is **Personal** by default, visible only to its author; the author may mark it **Shared with the parish priests**, which shows it to the priests serving that parish at the time it is read. Notes written before this rule went, still personal, to the parish priest, and no migration ever makes a personal note shared. Calendar events can be public, visible to selected groups, or restricted to parish office and clergy. Masses can have assigned priests and a clergy-only printable schedule. "Print my schedule" (calendar and dashboard) and "Priest schedule" open a dialog — a week or period to choose, what to include, a live count — and print a laid-out A4 sheet without opening a new tab. Service plans use an explicit Save action, chronological item times, and a total duration. Group attendance is recorded per member and meeting in a matrix, with retained former-member history; individual Mass attendance is not collected. Formation means the group's training or faith-development milestones. Registration forms link to explicit eligible events; when the event is not in the calendar yet, it can be described inside the new-form drawer (its room is checked against the calendar, room bookings and maintenance blocks) and is created together with the form; check-in is a separate arrival record for registrants of the selected event. Existing unlinked forms and check-in records are preserved but must be linked or migrated before use in the new event-based flow. Consent fields stay in person data. Anniversaries derive from registered baptism, chrismation, first Communion, and marriage entries, with earlier marriage reminders labelled legacy. The volunteer rota is one row of team columns that scrolls sideways, with full-size cards; drag and drop works across it. Facilities: each room's Availability opens a month calendar to pick any day, the day's bookings and free slots on a 07:00–23:00 strip (with set-up time), and a Book button on every free slot (earlier days are shown for reference and cannot be booked); each room card has its own "Block for maintenance", which lists the bookings that fall inside the chosen dates; Equipment has a search and an All / Available now / On loan / Needs attention filter. In Forms & workflows, each step of a task shows when it was done, clicking a task opens it, finishing its last step closes it, a task can be cancelled (with Undo), and each workflow is paused or resumed on its own. Record history shows times in the viewer's local time.

### Appearance

Each account chooses how its own dashboard looks under **My account → Appearance**: one of eight colour schemes (Forest, the default, Navy, Marian blue, Burgundy, Liturgical purple, Teal, Cedar brown, Slate) or any colour of its own, in Light, Dark or Same as this device mode. The choice previews immediately, is saved with the account (`settings` scope `user`, key `theme`) and follows it to every device; nobody else's screens change. `assets/theme.js` derives every colour token from the one colour and darkens text where needed for WCAG AA contrast in both modes. The public website (directory and parish pages) uses one shared website theme for every parish. A colour a parish chose earlier (`PARISH.theme`) stays stored but no longer changes anyone's screens. Certificates and printed pages keep their dark ink.

### Lists and calendars

Full lists and card collections show 10 items a page. Search, filters, sorting and totals work on the whole collection before paging, and changing page keeps the filters. Calendars share one pattern: **Month** and **Week** (grouped by day) with previous, next and today; a separate **List** with upcoming items nearest first and past items newest first; and search by name and by date.

## ParishLife version 2

Version 2 adds, on both servers (`server.py` and `cloudflare/src/`), with the same rules:

- **Scoped roles and administration** — super admin, bishop, diocesan admin, parish admin, priest, secretary, treasurer, ministry leader, and member or follower links; permission templates; a clergy registry with titles and their history (only the bishop changes a title) and service assignments; an **Administration** console limited to each person's authority. Nobody hands on a permission they do not hold or appoints at or above their own role.
- **Scoped deactivation** — a parish stops access to itself, a diocese to its parishes, and only the super admin suspends an account everywhere; a narrower reactivation never lifts a wider suspension. People → Archived became Deactivate / Reactivate, with all history kept, and the Online / New labels are gone from people lists and profiles.
- **Ministries** — public ministry profiles without leaders' phone numbers or email addresses; a guest interest form that makes nobody a member; applications approved by the ministry leader and then the parish priest; private departure requests seen only by the parish priests.
- **Documents** — baptism, First Communion, confirmation and marriage certificates requested without an account, with a private tracking link; the priest's signature and the bishop's acceptance as separate steps; a release policy the bishop sets (not decided by default: no automatic release); a read-only finance overview for the super admin and bishops.
- **Privacy** — private messages as cards in conversations with a person, a parish office or a ministry, with no editing or deleting and per-account archiving; a super admin can open one reported conversation only with a recorded reason, which is audited. Complaints reach only the recipients the submitter chose.
- **Plans** — twelve modules per parish, bundles, diocesan arrangements and change requests, and a public **Plans for parishes** page without prices. A plan switches intake and navigation on or off; it never grants or removes a permission, and a parish without a chosen plan keeps every module.
- **Public website** — one shared theme; the directory has List and Map views with shared filters and optional use of the visitor's location; fuller parish pages with clergy, office hours, directions, accessibility, a gallery and **View more** pages. Demonstration parishes carry a notice, and illustrative images are labelled.

### Configuration

Integrations stay off, and say so on screen, until they are configured. Environment variables (for the Worker: variables or secrets on the Worker):

| Variable | Used for |
| --- | --- |
| `PARISHLIFE_EMAIL_WEBHOOK`, `PARISHLIFE_SMS_WEBHOOK` | HTTPS endpoint of the email or SMS delivery service that sends verification codes, invitations and tracking links. Without one nothing is sent. |
| `PARISHLIFE_DELIVERY_TOKEN` | Optional bearer token sent to those endpoints. |
| `PARISHLIFE_PUBLIC_URL` | The site's public address; needed for provider sign-in redirects and links in messages. |
| `PARISHLIFE_GOOGLE_CLIENT_ID` / `_SECRET`, `PARISHLIFE_APPLE_CLIENT_ID` / `_SECRET`, `PARISHLIFE_MICROSOFT_CLIENT_ID` / `_SECRET`, `PARISHLIFE_MICROSOFT_TENANT` | Google, Apple and Microsoft sign-in (OpenID Connect). Each provider is offered only when its ID, secret and the public address are set. |
| `PARISHLIFE_GOOGLE_MAPS_KEY` | Browser key for the directory map. Without it the map is a labelled preview drawn from the coordinates parishes published. |
| `PARISHLIFE_SECURE_COOKIE=1` | Marks the session cookie Secure when served over HTTPS. |

Two decisions are left to the operator and are recorded as undecided until made: each diocese's certificate **release policy** (set by the bishop in Administration), and whether the **Public Presence** module includes guest document requests (set by the super admin under Plans; until decided, parishes keep taking them as before).

### Migrations

Every version 2 change to the database is additive and runs once at start-up (`server.py`) or on the Worker's first request after a deploy, recorded in `schema_migrations`: new tables for role assignments, clergy, contacts, connections, conversations, plans and the rest; existing accounts copied into role assignments; earlier portal messages copied into conversations (originals kept); earlier pastoral notes kept personal; earlier complaint cases kept visible to exactly the people who could already see them; the seed parishes marked as demonstration parishes. Nothing is deleted. Back up the database before starting a newer version.

### Verification status

The version 2 changes were checked statically only: Python compilation, JavaScript syntax checks, import resolution and a review of the edited source. No automated tests, browser test suites or penetration tests were run for them; testing remains with the project owner. `backend/test_accounts.py`, `backend/test_notes.py` and the sign-up part of `cloudflare/test/differential.mjs` were updated to the version 2 account rules but not run; the other owner suites were written for version 1 and were not reviewed against every version 2 rule, so some may need updating before they pass. The Google Maps loader, provider sign-in and delivery webhooks have not been exercised against the real services.

## Database migration and operating limits

`init_db()` creates or updates the SQLite schema on startup. Existing stored parish state is migrated to preserve historic household relationships, add pastoral task fields, reusable event and service templates, event visibility and priest assignments, event-linked registration/check-in containers, service plans, meeting attendance maps, and register history/revision metadata. The normalized relationship tables are rebuilt with parish-scoped foreign keys. The old transfer collection and Preferred Name field are removed from migrated state. Back up an existing database before starting a newer version.

This is a local application baseline. Official register numbering, certificate templates, retention rules, and external parish verification need archdiocese approval before live administrative use. UI exports and communication controls do not constitute delivery integrations. Functional and syntax checks are appropriate for changes here; a penetration test was not requested or performed.

## Public website design

The site's address (`http://127.0.0.1:4399/`, the same page as `public.html`) opens the church directory and public parish pages; **Members portal** in the header leads to the sign-in for parishioners and parish staff, and the sign-in screen links back to the website. The design includes bilingual search and town filters, fixed photographic sections with mobile/reduced-motion fallbacks, and individual parish stories, published Mass information, events, announcements and contact details. **Member portal → Website content** manages the published sections. See [design and verification notes](docs/public-site-design.md) and the [reference-site audit](docs/reference-design-audit.md).
